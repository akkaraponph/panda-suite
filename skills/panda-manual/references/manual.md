# Manual structure and evidence

Use a title the audience recognizes, the intended role, environment/version when
known, prerequisites, and one bounded goal. Separate distinct journeys rather
than making a long sequence across unrelated roles.

For each step record:

| Field | Content |
| --- | --- |
| Action | Exact observed control label and input instruction |
| Outcome | Visible resulting state, or supplied documented expectation |
| Evidence | Browser observation, supplied document/capture, or unverified |
| Capture | Actual file reference, if a useful safe capture exists |

Put genuine screenshot links next to the relevant step. Keep a private evidence
ledger if provenance detail would distract end users. The published guide still
needs an accurate verification statement.

Document validation and recovery paths only when observed or supported by supplied
documentation; label the latter. If a step cannot be established, say what a
reviewer must observe rather than inventing a button or error message.

Example for supplied notes with no browser:

> **Draft from supplied evidence; not browser verified.** Enter a title in
> “Request title”, then select “Save draft”. The supplied notes say the page shows
> “Draft saved: ” followed by that title. Verify the starting route, current labels,
> and actual outcome in the test environment before publishing this guide as
> verified. No screenshots were captured.

Completion reporting includes the journeys covered, actual observations, captures,
unverified states, and the access needed to resolve them. Do not mark a guide
fully verified because a stakeholder requests that label.

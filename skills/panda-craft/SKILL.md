# Panda Craft

Compose the expertise. Preserve the discipline. Verify the outcome.

Coordinate the user's selected specialists while they retain their domain methods.
Craft owns the shared outcome contract and evidence across activities. It is an
optional instruction workflow, not a runtime, separate agent, or prerequisite for
other skills. General workflow selection belongs with Panda Lead when available;
focused tasks can use their specialist directly.

Example request (standalone Codex names; use the host's discovered selectors):

```text
$panda-craft $impeccable
Refine this dashboard's hierarchy, responsiveness and keyboard navigation.
Local UI edits are allowed. Preserve business logic and API contracts.
Inspect the rendered result within Impeccable's verification budget.
```

## Establish intent — Chanda (ฉันทะ)

Inspect the request, relevant current artifacts, and existing authorization.
Identify the intended outcome, deliverables, constraints, non-goals, and observable
acceptance criteria. Separate user requirements from assumptions and preferences.
For small tasks, keep this contract in a short working note rather than creating
a plan document. Reuse satisfactory prior work instead of restarting discovery.

An implementation request authorizes relevant reversible edits; carry that scope
forward without asking again. Investigation, review, and planning preserve source
unless edits were requested. Naming an execution specialist alone does not grant
edit permission. Publication, deployment, destructive operations, production
changes, and external side effects need authorization covering those actions.
Resolve contradictions that materially affect correctness or scope before the
dependent action; continue independent useful work while a decision is pending.

## Compose the selected skills

1. Identify the explicitly selected specialists and their activities. Read their
   actual instructions through the host's supported discovery/loading mechanism,
   using discovered names and paths, including plugin namespaces where required.
   External specialists are supported without copying their instructions here.
2. Order dependent activities and assign each a deliverable and completion check.
   Add supporting guidance only for an identified gap. With no specialist named,
   infer a clear focused match from available metadata or ask a targeted question
   if the choice changes the result. Avoid loading the whole catalog.
3. Apply host and user instructions first; within them, retain each specialist's
   methods, scope, tool restrictions, and verification budget. A specialist cannot
   enlarge authorization or override another activity's constraints. Surface a
   material unresolved conflict instead of inventing an instruction hierarchy.
4. If a specialist is missing, state what cannot be loaded. Continue feasible
   ordinary assistance with the limitation explicit; pause only dependent work.
   Never fabricate the missing instructions or claim that the specialist ran.

Reading instructions is instruction loading, not programmatic invocation or proof
of separate agent execution. Use native delegation only when available and
authorized. No custom state service, mandatory peer, or redispatch through Lead
is needed; keep essential task evidence in the current workflow.

## Execute with sustained focus — Viriya + Citta (วิริยะ + จิตตะ)

Perform authorized work using each selected specialist's method. Finish required
deliverables, preserve existing contracts and user edits, and keep attention on
the current acceptance criteria. A skill's output is an intermediate artifact
until the shared outcome is checked.

At an activity transition, carry only the objective and acceptance criteria,
verified facts and sources, current artifacts, decisions, unknowns, next bounded
action, remaining work, verification evidence, and exact authorization. Recheck
critical current state; current source and user instructions outrank a stale
handoff. Scale the record to the work rather than requiring a persistent ledger.

## Examine and adjust — Vīmaṃsā (วิมังสา)

Compare delivered work with every material acceptance criterion. Use actual
commands, rendered observations, or other domain evidence appropriate to the
specialist. Derive expected results from the requirement independently of the
implementation. A green suite may omit a requirement: inspect coverage and use a
focused discriminating check for material uncovered behavior when authorized.
Preserve supplied tests where their modification is outside scope.

If a check fails, identify what executed, the failed state, and supporting evidence
before a bounded correction. Re-run affected checks after an authorized change.
Respect the specialist's pass/retry ceiling across the whole task; reaching it
with unmet criteria means reporting the gap, not starting a new Craft polish
cycle. Repeated no-progress attempts call for reassessment, not blind retries.
Report unavailable tools and unrun checks precisely; static inference is not an
executed test. Continue useful authorized work that does not depend on the blocker.

These four Iddhipāda disciplines guide the work throughout, rather than imposing
four mandatory stages or skill loads. Their grounding is Buddhist Method; its
installed instructions are optional deeper guidance. At a specific uncertainty
verify the claim (Kalāma); for stubborn failures investigate causes (Yoniso
Manasikāra); for repeated decline reconsider the approach (Apāyakosalla).

## Finish with evidence

Stop when the requested outcome is achieved, or no further useful authorized work
is feasible within available capabilities and specialist limits. Report concisely:

- Outcome, delivered artifacts, and remaining work.
- Skills actually loaded or used, with unavailable selections distinguished.
- Checks actually performed and observed results, including failures and limits.
- Unmet criteria, unknowns, blockers, and a next action only where needed.

State **VERIFIED** when evidence covers all material requested criteria;
**PARTIALLY VERIFIED** when only some are established; **BLOCKED** when a named
dependency prevents the remaining useful work; or **NOT VERIFIED** when evidence
does not establish the outcome. Report implementation completeness separately:
a finished artifact alone is not proof of verification. Keep unfavorable evidence
and reconsider a preferred approach when the results contradict it.

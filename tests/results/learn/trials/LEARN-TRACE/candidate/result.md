The supplied implementation accepts an order into an in-memory queue, then processes it when someone calls `Worker.tick()`. It uses `MemoryStore`, not SQLite. Acceptance returns a 202 response tuple before saving or notifying; each later `tick()` performs its save and notification calls synchronously. Nothing in the supplied implementation starts a scheduler, thread, or worker loop. The original README description contradicts this code and explicitly warns readers to check it. The useful mental model is: **request → pending list → worker → stored row → notification**. The queue and store belong to one `build(notify)` result; the service and worker share the same pending list. Each new build creates fresh state. This is deferred processing, but the shown code has no durable queue or database. ([app.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/app.py:6), [storage.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/storage.py:1))

Here is the request path:

1. `post_order(service, body)` rejects a missing or otherwise falsy `id` with `(400, {"error": "id required"})`. That is the only explicit validation; it assumes a mapping-like body and does not validate item types. ([app.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/app.py:12))
2. `submit` appends `{"id": order_id, "items": list(items)}` and returns `{"id": order_id, "status": "queued"}`. Missing items default to an empty list. `list(items)` copies/converts the supplied iterable; unsuitable values can raise rather than produce a controlled validation response. `post_order` wraps a successful submission in a 202 tuple. These are plain functions; an HTTP server adapter is not shown. ([orders.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/orders.py:5), [app.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/app.py:15))
3. `tick()` returns `False` if there is no work. Otherwise, it removes the oldest queued event, saves it, calls the injected notifier with only the order id, then returns `True`. `MemoryStore.save` appends a shallow dictionary copy to its list of rows. ([worker.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/worker.py:7), [storage.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/storage.py:5))
4. If either save or notification raises an `Exception`, the worker appends the event to the queue's tail and re-raises. It does not undo a completed save. A retry requires another caller invocation of `tick()`; there is no automatic retry timer, backoff, or attempt limit in these files. ([worker.py](/var/folders/dh/pyhpwt7x3y785l65wcc6gymh0000gn/T/panda-learn-eval-yrtv3w0m/LEARN-TRACE/candidate/input/worker.py:10))

| --- | --- | --- | --- |
| After `build(notify)` | `[]` | `[]` | Fresh service, worker, and store |
| Submit `O` through `post_order` | `[O]` | `[]` | `(202, {"id": "a", "status": "queued"})`; no notification yet |
| First tick: pop, then save | `[]` | `[O]` | First notification call receives `"a"` and raises |
| Exception handler | `[O]` | `[O]` | Original error propagates; save remains |
| Retry tick | `[]` | `[O, O]` | Saves again, notification returns, tick returns `True` |
| One more tick | `[]` | `[O, O]` | Returns `False` |

# Manager rejection implementation plan

Goal: add a manager rejection decision with a required reason, preserving the existing in-process approval API and its caller payloads.

Scope and sources: `requirements.md` supplies the requirements below; `service.py` and `test_service.py` establish current behavior. No HTTP server, database, persistence or network interface exists. Do not introduce routes, storage, retention policy or self-approval rules. This plan authorizes no implementation.

Requirements: **R1** managers can reject; **R2** rejection requires a non-empty reason; **R3** approved and rejected requests are terminal; **R4** preserve approval behavior and caller payloads; **R5** retain the fixture's local function boundary and excluded policy choices.

Current facts: `approve(request, actor)` first checks `actor["role"]`, raising `PermissionError("manager required")` for non-managers, then checks pending status, raising `ValueError("request must be pending")` otherwise. It returns a shallow copy with `status="approved"` and `reviewer_id=actor["id"]`; arbitrary other payload fields survive. `label(request)` reads only ID and status. Existing tests cover only successful approval status and denial of a member; they do not establish full payload compatibility or terminal transitions.

Proposed additive contract: `reject(request, actor, reason)` accepts the same request/actor dictionaries as `approve`, plus a required separate reason argument; existing caller dictionaries need no new fields. It checks manager role, then pending status, then reason, in that order. A reason must be a string containing at least one non-whitespace character. Invalid reasons raise `ValueError("rejection reason required")`; preserve the original valid string, including surrounding whitespace, in returned field `rejection_reason`. Return `{**request, "status": "rejected", "reviewer_id": actor["id"], "rejection_reason": reason}`. The function does not mutate either input. This reason representation and whitespace treatment are proposed implementation choices for R2, not existing policy inferred from the fixture.

Omitting the required argument raises Python's call-binding `TypeError` before function execution; explicit `None`, `""`, whitespace-only strings, or non-string values reach validation and raise the stated `ValueError` for an authorized pending request. Neither function promises new validation for malformed request/actor dictionaries: retain existing indexing behavior and required keys. Neither decision adds a self-approval comparison. The returned dictionary is the updated state; callers must use it for subsequent decisions. Terminality is enforced against the supplied state, as approval already does; there is no persistent identity, concurrency or stale-copy guarantee.

Affected files: `service.py` owns the additive function and existing approval/label behavior; `test_service.py` owns local unittest acceptance checks. No other application files or dependencies are needed. This plan is the only authored artifact so far.
